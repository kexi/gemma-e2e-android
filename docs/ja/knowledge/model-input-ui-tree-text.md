English: [../../knowledge/model-input-ui-tree-text.md](../../knowledge/model-input-ui-tree-text.md)

スクリーンショットは取得・保存しダッシュボードに表示しますが、モデルには渡しません。
テキストのみのプロンプトは小さく速く、UI ツリーには操作に必要な resource ID と
アクセシビリティラベルが既に含まれています。

*なぜ画像入力を使わないか:* Gemma 4 は画像を扱えるので精度が必要になれば解禁でき
ますが、トークンとレイテンシの実コストが伴います。

## 1回の判断が見るもの

エージェントはステートレスを保ちます。プロンプトは毎回、ゴール・これまでの経過・
現在の画面から組み立て直され、モデル側のコンテキストには何も持ち越しません。後の
ステップで必要になるものは、すべてそのプロンプトに載っている必要があります。深い
画面遷移に耐えるための要素が4つあります。

**履歴窓 30 ステップ。** ログインフォームより深いケースを回すようになった時点で
10 から引き上げました。10 では5画面奥にいるエージェントが、そこへ至った経緯を見
失い、既に否定したはずの分岐をたどり直してしまいます。それでも窓は有限のままです
— 無制限の履歴はプロンプトを膨らませ、レイテンシを破綻させます。

**窓の外に置く `remember` アクション。** 後で必要になる事実(確認コード、合計金額
など)をモデル自身が記録でき、以降のプロンプトすべてに `# Remembered facts` セク
ションとして提示されます。*なぜ履歴に載せるだけでは駄目か:* 履歴はスライドします
が、事実を記録するのは「周囲のステップより長生きさせたい」からこそです。ステップ
2 で読んだ値が、ステップ 40 のプロンプトにもまだ載っています。このアクションは端
末を一切操作しません。システムプロンプトでは「失われては困る値にのみ使う」ことを
明示しています。

**履歴行への画面署名。** 各行は `3. [.MainActivity] tap [2]` の形式になります。
取得元は `adb shell dumpsys window displays` の `mCurrentFocus`(遷移中で null の
場合は `mFocusedApp` にフォールバック)。これがないと、スタックをまたぐ 20 回の
タップと、同一画面での 20 回のタップが区別できません。ベストエフォートで、解析
できなければステップを失敗させず従来の署名なし形式に戻ります。*なぜ `displays`
で、素の `dumpsys window` ではないか:* どちらにも focus 行は含まれますが、素の
ダンプは window manager 全体の状態(実測 ~55KB 対 ~20KB)を毎ステップ引くことに
なります。

**ループガード。**(直列化した画面, アクションの記述)の組が2回連続で一致したら、
次のプロンプトに警告行を載せます。3回連続ならステップの note にも記録します。
*なぜ強制終了しないか:* verdict を下すのはモデルの役目であり、ヒューリスティック
で run を打ち切れば、時間のかかる復帰を偽の失敗に変えてしまいます。ハードストップ
は `maxSteps` だけです。

## 切り替え: 画面を XML で渡す

上のコンパクトなテキストはツリーそのものではなく、ツリーの読み取り結果です。面積
ゼロのノードを落とし、子が1つだけのラッパーを畳み、操作可能と判断したものにだけ
番号を振ります。この簡約で何を失い何を得ているかを測るため、ケースごとにパース済み
ツリーを XML のままモデルに渡せるようにしています。

**設定する場所。** `uiFormat: text | xml` をモデルと同じ順で解決します:
`case.uiFormat ?? scenario.uiFormat ?? UI_FORMAT`。`UI_FORMAT` が未設定または不明な
値なら `text` です。解決した値は `CaseRun` にモデルと並べて保存し、実行ページに
チップで表示します。切り替え導入前の実行には値がなく、`text` で動いています。
シナリオ編集画面では両方の階層で選べます(「画面の渡し方」)。

**モデルが見るもの。** `UiNode` ツリーの全ノードを入れ子のまま、何も刈り込まずに
渡します(面積ゼロのスペーサーやレイアウトのラッパーも含む)。属性名と順序は
uiautomator に合わせています(`text`, `resource-id`, `class`, `package`,
`content-desc`, `checkable`, `checked`, `clickable`, `enabled`, `focusable`,
`focused`, `scrollable`, `long-clickable`, `password`, `selected`, `bounds`)。
Android ではダンプそのものに `ref` を足したものになります。`checked` はテキスト
形式と同じく checkable なノードにだけ付きます。Web ページは忠実に対応するものが
ある属性だけを埋めます — input の `password`、`aria-selected` または `<option>` の
`selected`、checked 状態があるところの `checkable`、自身の overflow から判定する
`scrollable`。`package`・`focusable`・`long-clickable` は推測になるので付けません。

**ノードの呼び方。** 各ノードの `ref` 属性は全ノードを文書順(先行順)に数えた
位置です。画面内で一意で、すべてのノードを指定できます: `tap {ref: 12}` はノード
12 の中心をタップします。アクションのスキーマは変えず、文言だけが違います。
システムプロンプトでは、画面は XML ツリーであり、要素は `ref` 属性の番号を
`"ref"` として渡して指定する、画面にない ref を作らない、と伝えます。テキスト形式の
プロンプトとツール説明はバイト単位で変わっていません — ベンチマークはそれに対して
記録されており、テストがハッシュで固定しています。通信上でも確認済みです: スタブの
OpenAI 互換サーバーに対し、テキスト形式のリクエストは切り替え導入前と同一でした。
この確認で、compat-oai プラグインが各ツールの名前とパラメータは送るが説明は送らない
こともわかりました。実際には、形式ごとの文言がモデルに届くのはシステムプロンプト
経由です。

*なぜ uiautomator の XML そのものではないか:* Web ページには存在せず、共通の
`UiNode` ツリーから1つのシリアライザで出すほうが両プラットフォームを比較しやすい
ためです。その `index` 属性もノードを特定できません。兄弟の中での位置にすぎず、
実際の Kexi Coffee サインイン画面のダンプでは 14 ノード中 9 つが `index="0"` でした。
そのため `index` は書かず、`ref` で置き換えています。

*なぜ起動待ちはテキスト形式の ref を数え続けるか:* 最初のステップの前に、操作可能な
ものが描画されるまでポーリングします。XML 形式は全ノードに番号を振るので、何もない
起動直後のウィンドウでもすぐ準備完了に見えてしまいます。待機はテキスト形式の問いを
使い続け、その ref で操作することはありません。

### 既定をテキストのままにしている理由

2026-09-28 に Gemma 4 26B-A4B QAT(MLX)で、形式ごとに 1 回ずつ計測しました。
コミット済みの全シナリオを XML にすると 8 本中 7 本が成功し、Android のアクセシビリティ
ラボ(1 ケース 1 ペルソナ)が 4 ケース中 2 ケースで失敗しました。アイコンボタン 24 個が
並ぶ「Quick actions」画面(XML で約 2 万文字)で、モデルは「Next」ではなくアイコンを
押し続けて 13 ステップの上限を使い切り、1 ケースは戻るキーでアプリの外に出ました。
同じシナリオをテキストで流すと 4 ケースとも成功しました(8・8・8・12 ステップ)。
それ以外(ログイン、ショップ、Web のラボ、全ペルソナ一括のラボ)は XML でも全部成功し、
差は出ませんでした。

そのため XML はシナリオまたはケースごとに明示して使うものとし、サーバーの既定は `text`
のままにしています。*先に XML を短くしなかった理由:* 既定値の属性を省けば小さくなりますが、
それは計測し直すべき別の形式です。計測するまでは、ベンチマークで使ってきたテキストを基準にします。
