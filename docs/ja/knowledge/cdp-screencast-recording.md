Web のケースも Android と同じように録画される — ケースごとに 1 ファイル、
`var/videos/{runId}/{caseId}.mp4`、パスは `CaseRun` に載り、ダッシュボードで
再生でき、`RECORD_RUNS=0` で無効化できる。違うのは手段だけで、CDP には動画
キャプチャが無いため。ページが提供するストリームは `Page.startScreencast` の
base64 JPEG フレームだけなので、それを Matroska に包んで ffmpeg にパイプし、
MP4 にエンコードさせる。

ffmpeg は scrcpy と並んで `flake.nix` に宣言してあるので devshell に入っており、
インストール作業は不要。レコーダは `PATH` か設定されたパスから解決するので他の
入れ方でも動くが、確実なのは devshell。

*もっと良い手段が無いのか*: 無い。Playwright も Chromium の録画をこの API で
行っているので、見落としている非公開の経路は存在しない。
`HeadlessExperimental.beginFrame` は決定的なフレームを得られるが現行の headless
では事実上失われており、`getDisplayMedia` はページ側の API でパーミッション付与と
OS レベルのキャプチャが必要になる。

*scrcpy との比較*: 承知のうえで劣る。scrcpy はデバイスからハードウェア
エンコード済みの H.264 ストリームを引くが、こちらはフレームごとの非可逆 JPEG で、
エンコードと転送のオーバーヘッドにより上限は 30fps 程度、base64 で転送量も
1/3 増える。速いスクロールでは目に見えてフレームが落ちる。エージェントが何を
したかを説明する成果物としてはこれで足りるが、滑らかなデモ映像にはならない。

*なぜわざわざ Matroska に包むのか*: **screencast は画面が変化したときしか
フレームを送らない。** 10 秒間同じ画面に留まるケースはその 10 秒間まったく
何も送ってこない。素の MJPEG として流すとその間が消え、録画が実行より速く
進んでしまう — 「いつ何が起きたか」を見るためだけに存在する成果物としては
それでは用を成さない。そこで各フレームに自身のタイムスタンプを持たせた
Matroska ブロックに包み、固定 `-r` を与えた ffmpeg にフレームを複製させて
穴を埋めさせる。

*なぜ最後のフレームをタイマーで再送しないのか*: それはフレーム複製を
ユーザランドで再実装することであり、しかもタイムスタンプが既に述べている時刻
に対してドリフトする時計を使うことになる。Playwright も同じ結論に達しており、
ffmpeg が複製を行う旨をコメントに明記している。

*なぜ 1 フレーム 1 クラスタか*: ブロックのタイムコードはクラスタからの符号付き
16bit オフセットなので、フレームをまとめると、まさにこの設計が表現しようとして
いる長い静止区間でオーバーフローする。1 クラスタずつなら全オフセットがゼロで
済み、JPEG に比べれば数バイトの増加にすぎない。

*なぜセグメントをサイズ未定にするか*: 録画中に長さは知りようがない。`0x01` +
オール 1 が EBML の「ストリーム終端まで」であり、まさにこの状況を指す。

*なぜ全フレームを ack するか*: Chromium は未確定フレーム数に上限を設けており、
上限に達すると単に送信を止める。`screencastFrameAck` の漏れはストリームを遅く
するのではなく、ケースの途中で静かに終わらせる。ack はハンドラより先に送るので、
遅い購読者が他の購読者のストリームを止めることはない。

*なぜ 1 本だけ張ってユーザランドで配るか*: Chromium はページごとに screencast を
1 本しか許さない。2 回目の `startScreencast` は既存を「追加」ではなく「再設定」し、
どちらかの利用者が `stopScreencast` を呼べば両方に対して終了する。そこで
クライアントがページごとの購読者集合を持ち、最初の購読で開始し最後の解除で
停止する — 録画中のケースをライブビューでも見られるのはこの仕組みによる。

*なぜフレームが 0 枚のとき白フレームを書くか*: ffmpeg は空の入力からはファイルを
一切生成せず、`videoPath` が存在しないファイルを指してしまう。1 枚だけの録画は
退屈ではあるが、ページが一度も描画しなかったケースの正しい記録である。

*なぜ最後のフレームを 1 秒保持するか*: そうしないと判定が表示されている最後の
画面が 1 フレームで通り過ぎてしまう。

*なぜ寸法を偶数に丸めるか*: 多くのエンコーダが奇数を拒否するため。ビューポートは
サーバ配線で 1 度だけ宣言し、ページとコンテナの双方に渡している — コンテナが
実際のフレームと異なるサイズを宣言すると、引き伸ばされて再生されるか、
まったく再生できない動画になる。

*なぜ finalise 失敗を握り潰さず報告するか*: ffmpeg が閉じきらなかったファイルは
`moov` atom を持たず、どのプレイヤーでも開けない。したがって呼び出し側は再生
できないファイルへのパスではなく「録画なし」を報告しなければならない。scrcpy の
レコーダが同じ経路で辿り着いた結論と同じ
([per-case-screen-recording.md](per-case-screen-recording.md))。
